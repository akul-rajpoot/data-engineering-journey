

# Data Warehouse Notes

## Fact Table

A Fact Table stores:
- Business events
- Transactions
- Measurable metrics

Examples:
- Sales Amount
- Revenue
- Profit
- Quantity Sold
- Number of Orders

### Example: Fact_Sales

| Order_ID | Customer_ID | Product_ID | Date_ID | Amount |
|-----------|------------|------------|----------|---------|
| 1001 | 101 | 201 | 20250801 | 80000 |
| 1002 | 102 | 202 | 20250802 | 50000 |

### Key Characteristics
- Contains numeric measures
- Contains foreign keys to dimensions
- Usually very large
- Continuously grows

---

## Dimension Table

A Dimension Table stores descriptive information about business entities.

Examples:
- Customer
- Product
- Date
- Store
- Employee
- Region

### Example: Dim_Customer

| Customer_ID | Customer_Name | City |
|------------|--------------|------|
| 101 | Amit | Delhi |
| 102 | Rahul | Mumbai |

### Example: Dim_Product

| Product_ID | Product_Name | Category |
|------------|--------------|----------|
| 201 | iPhone | Mobile |
| 202 | MacBook | Laptop |

### Key Characteristics
- Descriptive attributes
- Smaller than fact tables
- Used for filtering and grouping data

---

## Fact vs Dimension

| Fact Table | Dimension Table |
|------------|------------------|
| Stores metrics | Stores descriptions |
| Contains numbers | Contains attributes |
| Large volume | Smaller volume |
| Example: Revenue | Example: Product Name |
| Example: Quantity Sold | Example: Customer City |

### Memory Trick

Fact = Something happened

Dimension = Tell me about it

---

## Star Schema

A Star Schema consists of:
- One central Fact Table
- Multiple Dimension Tables directly connected to the Fact Table

Example:

```text
           Dim_Customer
                 |
                 |
Dim_Product -- Fact_Sales -- Dim_Date
                 |
                 |
             Dim_Store
```

### Characteristics
- Denormalized dimensions
- Fewer joins
- Faster reporting queries
- Easy to understand
- Uses more storage

---

## Snowflake Schema

A Snowflake Schema is a normalized version of a Star Schema.

Example:

```text
Dim_Category
      |
Dim_Product
      |
Fact_Sales
      |
Dim_Customer
```

### Characteristics
- Normalized dimensions
- More joins
- Less storage
- More complex structure
- Slightly slower reporting queries

---

## Star Schema vs Snowflake Schema

| Feature | Star Schema | Snowflake Schema |
|----------|-------------|------------------|
| Joins | Fewer | More |
| Query Speed | Faster | Slower |
| Storage | More | Less |
| Complexity | Simple | Complex |
| Dimensions | Denormalized | Normalized |

# Surrogate Key vs Natural Key

## Natural Key

A Natural Key is a key that already exists in the business data and has business meaning.

### Examples

- PAN Number
- Employee Code
- Customer_ID from Source System
- Product Code
- Country Code

### Characteristics

- Comes from source/business system
- Has business meaning
- Can change over time
- Not recommended as primary key in a Data Warehouse

---

## Surrogate Key

A Surrogate Key is an artificial key generated by the Data Warehouse.

### Examples

- Customer_SK
- Product_SK
- Auto Increment ID
- Generated Sequence Numbers

### Characteristics

- No business meaning
- Generated by Data Warehouse
- Stable and does not change
- Preferred in Dimension Tables

---

## Example

### Dimension Customer

| Customer_SK | Customer_ID | Customer_Name |
|------------|------------|--------------|
| 1 | C101 | Amit |
| 2 | C102 | Rahul |

```text
Customer_SK = Surrogate Key
Customer_ID = Natural Key
```

---

## Natural Key vs Surrogate Key

| Feature | Natural Key | Surrogate Key |
|----------|------------|---------------|
| Business Meaning | Yes | No |
| Generated By | Source System | Data Warehouse |
| Can Change | Yes | No |
| Used In Dimensions | No | Yes |
| Used In Facts | No | Yes |

---

# Slowly Changing Dimensions (SCD)

SCD handles changes in Dimension Tables over time.

Example:

```text
Customer City
Delhi → Mumbai
```

Question:

```text
Keep history?
Or overwrite old value?
```

SCD Types answer this question.

---

# SCD Type 1

## Definition

Overwrite existing data.

No history is maintained.

---

## Example

### Before

| Customer_ID | Customer_Name | City |
|------------|--------------|------|
| C101 | Amit | Delhi |

### After

| Customer_ID | Customer_Name | City |
|------------|--------------|------|
| C101 | Amit | Mumbai |

---

## Characteristics

- Overwrites old value
- No historical tracking
- Simple implementation
- Less storage

---

## Advantages

- Easy to maintain
- Fast queries
- Minimal storage

---

## Disadvantages

- Historical data is lost

---

## Use Cases

- Name spelling correction
- Data quality fixes
- Non-historical attributes

---

# SCD Type 2

## Definition

Never overwrite existing records.

Create a new row whenever tracked attributes change.

History is preserved.

---

## Example

### Before

| Customer_SK | Customer_ID | City |
|------------|------------|------|
| 1 | C101 | Delhi |

### After

| Customer_SK | Customer_ID | City |
|------------|------------|------|
| 1 | C101 | Delhi |
| 2 | C101 | Mumbai |

---

## Real Data Warehouse Design

| Customer_SK | Customer_ID | City | Start_Date | End_Date | Current_Flag |
|------------|------------|------|------------|----------|-------------|
| 1 | C101 | Delhi | 2024-01-01 | 2025-05-31 | N |
| 2 | C101 | Mumbai | 2025-06-01 | NULL | Y |

---

## Characteristics

- Creates new row
- Preserves history
- Requires Surrogate Keys
- More storage

---

## Advantages

- Full historical tracking
- Accurate reporting
- Historical analysis possible

---

## Disadvantages

- More complex
- Additional storage required

---

## Use Cases

- Customer Address Changes
- Customer City Changes
- Employee Department Changes
- Employee Manager Changes

---

# Why Surrogate Key is Important in SCD Type 2

Suppose:

```text
Customer_ID = C101
```

Customer changes city:

```text
Delhi → Mumbai
```

Natural Key remains:

```text
C101
```

To store multiple historical versions, each version receives a different Surrogate Key.

```text
SK=1 → Delhi

SK=2 → Mumbai
```

This allows complete historical tracking.

---

# SCD Type 1 vs SCD Type 2

| Feature | Type 1 | Type 2 |
|----------|---------|---------|
| History Maintained | No | Yes |
| Overwrite Existing Row | Yes | No |
| New Row Created | No | Yes |
| Storage Required | Less | More |
| Complexity | Low | Medium |
| Historical Reporting | No | Yes |
